# patent skill 规则读取流程

> 本文档回答三个问题：`references/rules/` 为什么拆成这么多 md？LLM 在哪个阶段读哪个 md？读完写哪部分内容？
>
> 权威出处：`rules.md` 阶段读取表 + `SKILL.md` 各阶段 step。本文档是这两者的**流程视图**，不新增规则。

---

## 一、`references/rules/` 的 15 个 md 是什么

按「内容块 + 阶段」双重维度拆分，每个文件职责单一，避免 LLM 一次读全部。

| 分类 | 文件 | 管什么 |
|---|---|---|
| **全局** | `global.md`（264 行） | 所有阶段默认读取的全局硬规则（G1-G7） |
| **权要三章** | `claims-requirements.md`（109 行） | L1 权利要求书规则 |
| | `claims-field-background.md`（73 行） | L2 技术领域 + L3 背景技术 |
| **全文五章** | `abstract-figures.md`（80 行） | L4 说明书摘要 + L5 摘要附图 + L7 附图说明 |
| | `invention-content.md`（45 行） | L6 发明内容（含有益效果） |
| | `implementation.md`（122 行） | L8 具体实施方式 |
| | `figures.md`（46 行） | L9 附图（图 1 自动生成） |
| **执行层** | `docx-template.md`（107 行） | DOCX 模板 / XML / 格式 |
| **返修** | `revision.md`（147 行） | 返修、批注修订、学习闭环 |
| **评分机制** | `scoring.md`（116 行） | 评分卡（写入 DOCX 前闸门） |
| | `scoring-claims.md` / `scoring-content.md` / `scoring-global.md` / `scoring-impl.md` | scoring 的按路摘录（auditor 专用） |
| **索引** | `W-INDEX.md`（38 行） | W 编号索引（自动生成） |

**LLM 会一次读完所有 md 吗？——不会。**

按 `rules.md` 阶段读取表，是**按阶段渐进式读取**：
- 每阶段只读「必读核心」，不读「禁止默认读取」
- 有些文件「触发式按需」（命中触发条件才读）
- 审查阶段 auditor 用 `sed -n` **定向提取指定节**，不整篇 Read

## 二、完整流程：阶段 → 读哪些 md → 写哪部分

### 工作流 A：权要一稿（先写权利要求书三章）

```
┌─ 启动预读（rules.md 读取表）───────────────────────────┐
│ 必读：global.md（全局硬规则）                           │
│     + claims-requirements.md（L1 权利要求书）           │
│     + claims-field-background.md（L2 技术领域+L3 背景） │
│     + scoring.md（评分卡）                              │
│     + docx-template.md（仅 md 层条目，G8-0/G8-0b）      │
│ 禁止读：abstract-figures / invention-content /          │
│         implementation / figures / revision / cases     │
└─────────────────────────────────────────────────────────┘
   ↓
┌─ 撰写 docs/权要稿.md ───────────────────────────────────┐
│  权利要求书（1-10 条） ← 靠 claims-requirements.md L1   │
│  技术领域              ← 靠 claims-field-background.md L2│
│  背景技术              ← 靠 claims-field-background.md L3│
└─────────────────────────────────────────────────────────┘
   ↓
┌─ 审查闸门（写入 DOCX 前）───────────────────────────────┐
│ 阶段A 脚本：check_hard_rules.py + check_cross_block.py  │
│ 阶段B auditor（每路定向读自己的规则文件）：              │
│   claims-auditor → claims-requirements.md L1 节          │
│   global-auditor → global.md G3-G6 + L2/L3 + docx md 层  │
│ 主 agent 读：scoring.md（合并计分）                      │
└─────────────────────────────────────────────────────────┘
```

### 工作流 D：返修（老板批注 / Word 批注修订）

```
┌─ 预读（rules.md 读取表）──────────────────────────────┐
│ 必读：global.md + revision.md + docx-template.md        │
│     + scoring.md（触发返修定向审查闸门时）               │
│ 按批注内容定向读：                                      │
│   权要批注 → claims-requirements.md L1 / 背景 L2-L3      │
│   全文批注 → abstract-figures / invention-content /      │
│              implementation / figures                   │
│ 触发式：revision.md A4-0 触发块（删除类/算法类/序号类）  │
│ 禁止读：未被批注涉及的内容块规则                          │
└─────────────────────────────────────────────────────────┘
   ↓
┌─ 撰写 ─────────────────────────────────────────────────┐
│  只改批注涉及的块，其余不动（改写即替换，禁止新旧并存）  │
└─────────────────────────────────────────────────────────┘
   ↓
```

## 三、省 token 的三个机制

1. **渐进式读取**：每阶段只读必读核心，禁止读无关阶段规则——省 token 第一道闸。
2. **触发式按需**：`revision.md` A4-0、`cases/INDEX.md` 等命中触发条件才读，不命中不读。
3. **审查定向提取**：auditor 传文件路径 + `sed -n` 提取指定节，不整篇 Read——审查时规则全文不进上下文。

## 四、待办：最小撰写清单（当前优化方向）

**现状问题**：撰写阶段预读的是整份规则文件（如权要阶段读整份 `claims-requirements.md` 109 行），但 SKILL.md step 7 明令「主 agent 不预演自检清单」——**读了却不边写边用**，预读 token 未转化为撰写质量，写完靠脚本/auditor 扫出问题再回修。

**优化方向**（已与用户对齐，未实施）：

> 把撰写预读从「整份规则文件」改成「**最小撰写清单**」（10 条左右撰写必守），开写前读、每步写完对照自查；审查阶段照旧用全量规则定向扫。

**实施路径**：
1. **规则分类审计**：把 `claims-requirements.md`、`global.md`、`claims-field-background.md` 逐条标出「撰写必守（生成约束）」vs「审查扫描（事后 scan）」
2. **生成《撰写最小清单》**（`references/rules/writing-brief-<stage>.md`），只含撰写必守
3. **改 `rules.md` 阶段读取表**：撰写预读从「全量规则文件」改成「最小清单 + 触发式定向补充」
4. **保留审查阶段全量读取**，不动

> 注意：不能简单把硬规则从预读删除。硬规则分两类——「生成约束型」（如「每步输入→明确操作→输出」「权1主步骤≤5」）必须留在撰写清单，防止写歪；「审查扫描型」（如「权要总数=10」「每条只用一个句号」）适合后置。删错会伤质量。
