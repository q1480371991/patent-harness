# patent skill 规则读取流程

> 本文档回答三个问题：`references/rules/` 为什么拆成这么多 md？LLM 在哪个阶段读哪个 md？读完写哪部分内容？
>
> 权威出处：`rules.md` 阶段读取表 + `SKILL.md` 各阶段 step。本文档是这两者的**流程视图**，不新增规则。

---

## 一、`references/rules/` 的 17 个 md 是什么

按「内容块 + 阶段」双重维度拆分，每个文件职责单一，避免 LLM 一次读全部。

| 分类 | 文件 | 管什么 |
|---|---|---|
| **全局** | `global.md` | 所有阶段默认读取的全局硬规则（G1-G7） |
| **权要三章** | `claims-requirements.md` | L1 权利要求书规则 |
| | `claims-field-background.md` | L2 技术领域 + L3 背景技术 |
| **全文五章** | `abstract-figures.md` | L4 说明书摘要 + L5 摘要附图 + L7 附图说明 |
| | `invention-content.md` | L6 发明内容（含有益效果） |
| | `implementation.md` | L8 具体实施方式 |
| | `figures.md` | L9 附图（图 1 自动生成） |
| **执行层** | `docx-template.md` | DOCX 模板 / XML / 格式 |
| | `docx-scripts.md` | DOCX 辅助脚本清单（各 `scripts/*.py` 参数与语义；含 `boilerplate.py` 模板句唯一副本、`docx_assets.py`） |
| **返修** | `revision.md` | 返修、批注修订（学习闭环见 `rules.md`） |
| | `revision-docx.md` | 返修 DOCX 执行细则（审核稿到手 XML 实测三件事、留痕注入、返修执行纪律） |
| **评分机制** | `scoring.md` | 评分卡（写入 DOCX 前闸门） |
| | `scoring-claims.md` / `scoring-content.md` / `scoring-global.md` / `scoring-impl.md` | scoring 的按路摘录（auditor 专用） |
| **索引** | `W-INDEX.md` | W 编号索引（自动生成） |

> 行数不再写在本文档（旧值已多次漂移）；**各阶段实际读取量**用 `python scripts/rules_budget.py` 查看，超基线 10% 触发一次「这条新规则该不该进必读层」的审查（`rules.md` 阶段读取量预算条）。

**LLM 会一次读完所有 md 吗？——不会。**

按 `rules.md` 阶段读取表，是**按阶段渐进式读取**：
- 每阶段只读「必读核心」，不读「禁止默认读取」
- 有些文件「触发式按需」（命中触发条件才读）
- 审查阶段 auditor 用 `sed -n` **定向提取指定节**，不整篇 Read

## 二、完整流程：阶段 → 读哪些 md → 写哪部分

### 工作流 A：权要一稿（先写权利要求书三章）

```
┌─ 启动预读（rules.md 读取表）───────────────────────────┐
│ 必读：global.md（全局硬规则）                           │
│     + claims-requirements.md（L1 权利要求书）           │
│     + claims-field-background.md（L2 技术领域+L3 背景） │
│     + scoring.md（评分卡）                              │
│     + docx-template.md（仅 md 层条目，G8-0/G8-0b）      │
│ 禁止读：abstract-figures / invention-content /          │
│         implementation / figures / revision / cases     │
└─────────────────────────────────────────────────────────┘
   ↓
┌─ 撰写 docs/权要稿.md ───────────────────────────────────┐
│  权利要求书（1-10 条） ← 靠 claims-requirements.md L1   │
│  技术领域              ← 靠 claims-field-background.md L2│
│  背景技术              ← 靠 claims-field-background.md L3│
└─────────────────────────────────────────────────────────┘
   ↓
┌─ 审查闸门（写入 DOCX 前）───────────────────────────────┐
│ 阶段A 脚本：check_hard_rules.py + check_cross_block.py  │
│ 阶段B auditor（每路定向读自己的规则文件）：              │
```

### 工作流 D：返修（权要二稿/三稿、全文二稿/三稿；老板批注 / Word 批注修订）

同一套返修编排覆盖两类稿次：**权要二稿/三稿**（工作对象 `docs/权要稿.md`，不做冻结块体检）与**全文二稿/三稿**（工作对象 `docs/全文稿.md`，权要已单独定稿时先做冻结块只读体检）。规则读取按 `revision.md`「返修节级读取表」定向提取，不整篇读阶段规则。

```
┌─ 预读（rules.md 读取表 + revision.md 节级读取表）──────┐
│ 必读核心：global.md + revision.md + docx-template.md    │
│     + scoring.md（触发返修定向审查闸门时）               │
│ 按批注命中块 sed -n 定向提取（不整篇 Read）：            │
│   权要条文 → claims-requirements.md L1 节                │
│   技术领域/背景 → claims-field-background.md L2/L3 节    │
│   摘要/附图说明 → abstract-figures.md L4 / L7 节         │
│   发明内容 → invention-content.md L6 节                  │
│   具体实施方式 → implementation.md L8 节 + global G6-1   │
│   附图 → figures.md L9 节                                │
│ 镜像块联动：命中权要条文或 L8 步骤改动时，五处镜像块      │
│   对应节自动并入（同步义务不因读取粒度变化而减少）        │
│ 触发式：revision.md A4-0 触发块（删除类/算法类/序号类）  │
│ 禁止读：未被批注涉及的内容块规则                          │
└─────────────────────────────────────────────────────────┘
   ↓
┌─ 撰写 ─────────────────────────────────────────────────┐
│  只改批注涉及的块，其余不动（改写即替换，禁止新旧并存）  │
└─────────────────────────────────────────────────────────┘
   ↓
┌─ 返修定向审查闸门 ─────────────────────────────────────┐
│ 入口守卫：timestamp_guard（两类工作流均跑）              │
│   + fingerprint_claims --check（仅权要已冻结的分离式）   │
│ 机械脚本强制，无条件跑两套共 5 个：                      │
│   权要稿.md → check_hard_rules + check_cross_block       │
│              （--stage claims-draft）                    │
│   全文稿.md → check_hard_rules + check_cross_block       │
│              + verify_claims_alignment（--stage full-draft）│
│   （权要两脚本不可省：全文稿.md 不含权利要求书章节，      │
│     省掉即 L1 机械规则全套静默跳过）                      │
│ auditor 语义复核：询问用户，获同意才以增量复核模式调用   │
│   （全文返修三路、权要返修两路）                          │
└─────────────────────────────────────────────────────────┘
```

### 交付前收尾三脚本（各工作流通用，顺序固定）

```
python scripts/boilerplate.py check --md docs/全文稿.md --claims-md docs/权要稿.md   # 模板句逐字（含介质禁写项）

python scripts/verify_docx_skeleton.py <交付稿.docx> --stage 全文 --invention-name "<给定名称>"  # 骨架/分节/标题/行距/空段/名称
```

**任何 Word/WPS 手工编辑（贴 Visio 图、改字）之后必须重跑第三项**——应用再保存会把继承的缩进值物化（名称段 `firstLine=643` 即由此产生；清了要重跑复核）。权威出处：`SKILL.md` 各工作流 step 与 `docx-scripts.md`。

## 三、省 token 的三个机制

1. **渐进式读取**：每阶段只读必读核心，禁止读无关阶段规则——省 token 第一道闸。
2. **触发式按需**：`revision.md` A4-0、`cases/INDEX.md` 等命中触发条件才读，不命中不读。
3. **审查定向提取**：auditor 传文件路径 + `sed -n` 提取指定节，不整篇 Read——审查时规则全文不进上下文。

## 四、待办：最小撰写清单（当前优化方向）

**现状问题**：撰写阶段预读的是整份规则文件（如权要阶段读整份 `claims-requirements.md` 109 行），但 SKILL.md step 7 明令「主 agent 不预演自检清单」——**读了却不边写边用**，预读 token 未转化为撰写质量，写完靠脚本/auditor 扫出问题再回修。

**优化方向**（已与用户对齐，未实施）：

> 把撰写预读从「整份规则文件」改成「**最小撰写清单**」（10 条左右撰写必守），开写前读、每步写完对照自查；审查阶段照旧用全量规则定向扫。

**实施路径**：
1. **规则分类审计**：把 `claims-requirements.md`、`global.md`、`claims-field-background.md` 逐条标出「撰写必守（生成约束）」vs「审查扫描（事后 scan）」
2. **生成《撰写最小清单》**（`references/rules/writing-brief-<stage>.md`），只含撰写必守
3. **改 `rules.md` 阶段读取表**：撰写预读从「全量规则文件」改成「最小清单 + 触发式定向补充」
4. **保留审查阶段全量读取**，不动

> 注意：不能简单把硬规则从预读删除。硬规则分两类——「生成约束型」（如「每步输入→明确操作→输出」「权1主步骤≤6」）必须留在撰写清单，防止写歪；「审查扫描型」（如「权要总数=10」「每条只用一个句号」）适合后置。删错会伤质量。

## 五、维护纪律：大改后跑两路独立复核（2026-09-11 定）

> 唯一出处＝`rules.md`「大改后的两路独立复核」条；本节只写**怎么做**（怎么起、要什么、怎么收口）。

**触发条件（满足任一）**：①一次改动跨 ≥5 个文件；②涉及口径变更（配比／阈值／区间／合法性判定改变）；③动了脚本判定逻辑（阈值、白名单、新增规则）。小改（单文件措辞、单条 typo）不触发。

⚠️ **触发不等于必跑**：命中条件时**先问用户（说明命中哪一条、预计成本），由用户决定跑不跑**——本纪律不自动执行。

**怎么起**：用 `Agent` 工具**并行起两路** subagent（各自全新上下文，不知道改动意图——独立的价值就在这里）：

| 路 | 分工 | 读什么 |
|---|---|---|
| 第 1 路·权要侧 | 权要/模板/权要脚本 | `claims-requirements.md`、`boilerplate.py`、`check_hard_rules.py`（权要规则）、`check_cross_block.py`、`agents/claims-auditor.md`、`tests/` |
| 第 2 路·说明书侧 | 说明书/审计体系 | `implementation.md`、`global.md`、`invention-content.md`、`claims-field-background.md`、`docx-template.md`、`scoring*.md`、其余契约、`SKILL.md` |

**要什么（写进 prompt）**：①**只读不改**；②每条发现必须给 `文件:行号` + **两处原文摘录**（A 处与冲突的 B 处）+ 冲突性质；
③**另列一节「已核对一致项」**（逐条列出核对过且一致的项——防「0 问题」式假绿灯；执行要求唯一出处 `rules.md`「大改后的两路独立复核」条）；
④单列「疑似冲突需人工确认」节。

**怎么收口**：①**逐条回原文核实**再动手（AI 会报不存在的冲突——本轮实测至少 1 条误报）；④**收尾跑四个守卫**：`verify_rule_anchors.py`（契约锚点）、`verify_scoring_excerpts.py`（scoring 摘录编号分派）、`rules_budget.py --check`（读取量预算）、`verify_w_index.py`（`W-INDEX.md` 与规则文件一致）——**四者全绿才算收口**（2026-09-11 教训：评分摘录守卫坏了无人知，因为改了 `scoring-*.md` 却没跑它；2026-09-19 同型：`W-INDEX.md` 无守卫，30 行被改坏 17 行无人知）；
②真冲突 → 修；③误报 → 不改，但要把**导致误报的表述**也理顺（否则下次还会被报）；
④结论与处置记入 `docs/维护记录-*.md`（含"哪条是误报、为什么"）。

**成本参考（2026-09-11 实测）**：两路各约 6 分钟、合计约 40 万 subagent token，报回 16 + 20 条，去重后处置 24 处。
**收益形态**：抓的是**语义层矛盾**（示例必填↔非必需、允许形态被硬判 FAIL、核项归属错路、规则条文缺失），
关键词扫描扫不出来。
