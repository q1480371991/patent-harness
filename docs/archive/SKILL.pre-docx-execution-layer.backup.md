# 专利撰写工作流

本 skill 用于用户在 `/Users/example/Desktop/Patent/` 下的专利撰写工作流。

## 必读

在撰写或修订前，必须阅读本目录下的 `rules.md`。它是本工作流的强制写作规范。

## 默认立场

- 默认中文撰写，除必要的英文缩写、模型名、公式符号、技术术语外。
- 没有交底书 DOCX 时不要凭空起稿。
- 不要机械照抄交底书；提取技术问题、技术方案、技术效果。
- 若交底书逻辑不连贯、无法支持一个干净的权要集，停下来询问用户，不要凭空发明。
- 用户没明确要求时，不另外输出独立的撰写检查报告。
- 用户明确要求只读分析、规则检查、经验总结或修改建议时，不生成 DOCX，不改动案件文件。

## 阶段判断

根据用户表述和案件文件夹里的现有文件判断当前阶段：

| 用户意图 | 阶段 | 输出版本 |
|---|---|---|
| 第一次撰写权要，权要一稿 | claims draft | `案件号-权要1稿-作者-发明题目全称.docx` |
| 老板对权要稿给批注 | claims revision | 下一稿 `权要2稿` 或 `权要3稿` |
| 权要已定，写全文 | full draft | `案件号-全文1稿-作者-发明题目全称.docx` |
| 老板对全文稿给批注 | full revision | 下一稿 `全文2稿` 或 `全文3稿` |

如果缺以下任一元数据，应主动询问用户：案件号、作者名、发明题目、案件文件夹、当前阶段。不要在缺信息时凭猜测填。

## 案件文件夹约定

用户通常会在 `/Users/example/Desktop/Patent/` 下新建一个案件文件夹，把交底书 DOCX 放进去。该文件夹通常只有一份交底书 DOCX 和一份专利 DOCX，命名清晰。

自动识别明显文件。如果有多个可能候选，请用户选择。

## 权要一稿

`权要一稿`：

1. 用 `scripts/disclosure_docx_to_md.py` 把交底书 DOCX 转为带批注的 Markdown，保存为案件文件夹下的 `交底书.md`。
2. 深读 `交底书.md`，包括 `==高亮==` 内容和 `> 💡 [批注 ...]` 行。
3. 提取核心技术问题、创新逻辑、关键步骤、特征命名、数据来源、数据用途、批注/高亮、预期效果。
4. 先用 Markdown 把专利稿件写在案件文件夹下的 `权要稿.md`。
5. **权要一稿仅撰写并展示三部分，按此顺序排列**：权利要求书 → 技术领域 → 背景技术。其他章节（说明书摘要、摘要附图、发明内容、附图说明、具体实施方式、说明书附图）一律留到全文一稿撰写，权要一稿阶段不要写入 `权要稿.md`，也不要在 DOCX 正文或页眉中显示。
6. 在 `权要稿.md` 中写完整的权要集（通常 8–10 条，含独立权要和从属权要），技术领域单段，背景技术含现有技术描述 + 推导 + 一个具体缺点 + 技术问题。若题目同时包含方法和系统/装置，通常采用方法独权、方法从权、系统/装置独权及其从权的结构；方法权通常写到权要 7，系统/装置权通常保留 2–3 条，实际编号和数量按案件技术逻辑、老板批注和保护策略调整。
7. 权要字数、断行和依附关系必须参考 `/Users/example/Desktop/Patent/第3-4课的案例资料/案例分享-定稿-一种基于物联网的智能电能表数据采集方法及系统.docx`：权要1不超过400字；从权使用“权要编号开头段 + 2–5个短步骤段”的粒度，避免把多个实施细节挤成长段；每个分号必须保留在段末并另起一行；从属权要应按技术逻辑形成“分支 + 局部链条”的多元化依附关系，不得机械全部依附权要1，也不得机械写成刚性顺序链。例如可出现“权2、权3、权4补充权1；权5补充权3；权6补充权5；权7补充权6；权8补充权3；权9补充权8；权10作为另一保护主题独权或系统/装置权”的结构，但实际依附关系应按案件技术逻辑调整。
8. 若撰写摘要（仅全文一稿或用户明确要求时），摘要字数不超过300字；权要一稿默认不写摘要。
9. 写入 DOCX 之前，对 `权要稿.md` 自检：术语一致性、权要引用、数据来源/用途、禁用措辞、权要内公式、模型/阈值缺失、权要1字数、分号换行、是否误写了权要一稿以外的章节。
10. 把 `/Users/example/Desktop/Patent/模板.docx` 拷贝到案件文件夹。
11. 把拷贝出来的文件重命名为 `案件号-权要1稿-作者-发明题目全称.docx`。
12. **保留模板的全部骨架结构**：保留与原模板一致的分节断点 `sectPr`、全部 `word/header*.xml` 和全部 `headerReference`（当前模板实测为 5 个 `sectPr`、13 个 `header*.xml`；主章节标题挂在页眉上，不要删页眉文件，不要删 headerReference）。
13. **本稿最终 DOCX 只能显示"权利要求书"页眉和"说明书"页眉，以及正文中的发明名称、技术领域、背景技术**。说明书摘要、摘要附图、发明内容、附图说明、具体实施方式、说明书附图、图1等标题或占位内容不得显示；不能仅留空正文而保留这些页眉/标题。
14. 写入 DOCX 时，基于模板样式重组可见章节：保留 `word/header*.xml` 等包内资源，但正文结构只保留权利要求书分节和说明书分节；权利要求书分节使用模板的“权利要求书”页眉，说明书分节使用模板的“说明书”页眉。
15. 完成后做 XML 层级验证：可见页眉文本仅包含“权利要求书”“说明书”；DOCX 正文不得出现“说明书摘要”“摘要附图”“发明内容”“附图说明”“具体实施方式”“说明书附图”“图1”；权要书节文本无模板蓝字残留（如"特征 1""智慧农业"）；技术领域+背景技术节文本已替换；权要1不超过400字；所有含分号的段落均以分号结尾。
16. 仅报告：输出 DOCX 路径、`交底书.md` 路径、`权要稿.md` 路径，以及任何需要用户关注的问题。不出独立的撰写检查报告。

## Word 批注修订

`权要二稿/三稿` 或 `全文二稿/三稿`：

1. 打开老板批注过的 DOCX。
2. 从 `word/comments.xml` 提取 Word 原生批注，必要时配合 `word/document.xml` 中被引用的文本。
3. 在编辑前先把批注稿拷贝为下一稿对应版本。
4. 在拷贝出来的文件中逐条应用老板的批注修改。
5. 修订完成后清除修订稿中的所有批注。
6. 不要覆盖老板批注过的原文件。
7. 报告修订稿输出路径。

老板批注与硬性规则同源；修订时以批注为准。如果某条批注与可实施性或强制规则冲突，停下来询问用户，不要静默违反任何一方。

## 全文一稿

`全文一稿`：

1. 从已审权要稿开始，不从空白模板起稿。
2. 除非用户要求改动，保留已审权要不变。
3. 先用 Markdown 把全文扩展内容写到案件文件夹下的 `全文稿.md`，**补全**权要一稿时未写的章节：说明书摘要、摘要附图、发明内容、附图说明、具体实施方式、说明书附图（图 1 等）。
4. 在说明书中解释每一条权要步骤。
5. 加入有益效果的技术原因。
6. 在 `全文稿.md` 末尾追加 `## 附图设计（供手画 Visio 用）` 一节，按 `rules.md` 中的附图设计规则执行（规则 A 主流程基于权要 1、规则 B 子流程基于展开的主步骤、规则 C 系统结构基于系统权要）。用户根据这一节在 Visio 中手画实际附图，本 skill 不输出图片文件。
7. 写入 DOCX 之前，对 `全文稿.md` 自检：权要保留、术语一致性、模板案例性术语、禁用措辞、公式、模型/阈值细节、可实施性，并核对附图设计节的附图清单和节点数与权要 1、子步骤编号、系统权要相吻合。
8. 把已审权要稿前向拷贝为 `案件号-全文1稿-作者-发明题目全称.docx`。
9. **保留模板骨架**（分节断点 `sectPr`、全部 header*.xml、headerReference 均与原模板一致）。在权要一稿留空的"说明书摘要节"、"摘要附图节"、"说明书附图节"，以及说明书节内权要一稿留空的"发明内容/附图说明/具体实施方式"段落区填入内容。**不要清空 body 重建**。
10. 报告完工前，应用 DOCX 格式并完成 XML 层级的验证（sectPr 数、header 数、各章节文本是否到位）。

## DOCX 处理注意事项

使用安全文件操作：

- 编辑前先拷贝
- 保留原审过的文件
- 权要一稿和全文一稿，写 DOCX 前确认对应的 `权要稿.md` 或 `全文稿.md` 存在
- 写完后验证输出文件存在
- **不要清空 body 段落重建**：模板用分节断点（sectPr）和 `header*.xml` 把主章节标题（说明书摘要、摘要附图、权利要求书、说明书、说明书附图）挂在页眉上，body 内仅有正文区。清空 body 等于摧毁这套骨架。正确方式是**保留与原模板一致的 sectPr、header*.xml、headerReference**，**就地替换**段落文本。
- 清除批注时，验证 `word/comments.xml` 已不存在或确认没有遗留批注

辅助脚本：

- `scripts/disclosure_docx_to_md.py --input <交底书.docx> --output <案件文件夹>/交底书.md`
- `scripts/inject_md_to_template.py` **(老脚本会清空 body，不要直接用于权要一稿/全文一稿；如需使用，先确认其新版已改为就地替换模式)**

读取 DOCX 中的文本、批注、格式或关联关系时，可用把 DOCX 当 ZIP/XML 处理的小型 Python 片段。优先用 zipfile + xml.etree 直接读写 `word/document.xml`，按段落 index 或文本内容做就地替换。

## 完工报告

最终报告简短即可：

- 输出文件路径
- 完成阶段
- 修订模式下是否清除了批注
- 是否有未解决的需要用户澄清的事项

默认不输出冗长的撰写检查报告。
