# 专利撰写规则

以下规则在本用户的专利撰写与修订工作流中为强制规范。

## 文件命名

### 案件内工作文件

- 交底书 DOCX 转出的带批注 Markdown 统一命名为：`交底书.md`。
- 权要阶段 Markdown 草稿统一命名为：`权要稿.md`。
- 全文阶段 Markdown 草稿统一命名为：`全文稿.md`。
- 第一次提交后的权要批注稿，用户通常命名为：`权要1稿-修注.docx`。
- 旧的 `disclosure_annotated.md`、`case_draft.md` 命名不再作为标准；遇到旧案时应规范化改名，避免同一案件中多个草稿名并存。

### 对外 DOCX 交付文件

采用：

`案件号-稿次-作者-发明题目全称.docx`

示例：

- `案件号-权要1稿-王xx-xx方法及装置.docx`
- `案件号-权要2稿-王xx-xx方法及装置.docx`
- `案件号-全文1稿-王xx-xx方法及装置.docx`
- `案件号-全文2稿-王xx-xx方法及装置.docx`

## 核心撰写逻辑

- 不要原文照抄交底书。
- 撰写或返修前必须先充分理解交底书，至少能复述本案技术链条、关键特征的来源与用途、创新点和预期效果；未理解清楚时不得起草或返修。
- 锁定一个工业可行的技术问题。
- 围绕"技术问题—技术方案—技术效果"展开。
- 背景技术必须描述一个具体的现有技术，由该现有技术推导出缺陷，再过渡到本发明的创新点。若交底书未交代清楚现有技术，先去检索一个合适的现有技术再写背景技术。
- 背景技术的现有技术部分应列举具体方法或技术名称，避免只写“现有技术”“常规方法”等空泛表述；缺陷段应一语点中待解决问题，避免反复铺陈应用价值、危害后果或多个并列缺陷。
- 特殊情形下，若文档标注了某关键词必须出现在背景技术，选一个合适的关键词在背景技术中出现一次。
- 发明内容中，从交底书选两个合适的创新点，应与背景技术中所提的技术问题相对应；若另一步骤更合适则替换，不要机械照搬同事的措辞。
- 权利要求 1 必须解决该技术问题。
- 从属权要描述权要 1 各步骤的具体实施方式。
- 若交底书逻辑不通或技术上不自洽，停下来询问用户。

## 批注返修纪律

- 返修前先读取批注稿和交底书，确认批注所指问题与交底书技术内容的对应关系；不能只看批注局部文字就直接改。
- 批注返修应按批注要求做外科式修改，不得擅自重写整套权要、改变保护主题、增加批注未要求的新技术特征或扩展新的方案分支。必要联动修改不属于擅自扩写，但必须能直接追溯到该批注导致的编号迁移、引用关系、前序基础、方法-系统对应或被拆分保护点同步。
- 若批注要求删除、拆分或补充某一特征，只修改该特征所在权要及受其前序引用影响的必要位置；权要 1、权要 2 等已有结构只有在批注明确要求或引用关系必须联动时才调整。
- 批注之间存在冲突，或批注要求与交底书无法对应时，先向用户确认，不要自行发明内容补齐。
- 对老板批注的返修经验应沉淀为规则：如果批注指向“引用不完整”“所述使用”“链条断裂”“创新步骤太概括”“阈值循环依赖”“系统权与方法权不对应”等问题，返修时不仅改被批注句，还要检查同类问题在同一权要集中的必要联动位置。
- 若老板对某一段权要结构作出颠覆式调整，先重新核对最终权要总数、编号迁移、被删除权要和新旧保护点对应关系；不得根据旧稿编号臆测修改对象。
- 总结经验时必须同时对比原稿、返修稿和 comments.xml 中的批注锚定文本；不能只看用户转述或单个段落。

## 权利要求

- 权利要求要清楚、简明、准确、唯一、有层次。
- 默认撰写 8–10 条权要；当题目同时包含方法和系统/装置时，通常采用“方法独权 + 方法从权 + 系统/装置独权及其从权”的结构。方法权通常写到权要 7，系统/装置权通常保留 2–3 条；若技术保护点、老板批注或案件策略需要，可扩展方法权数量或压缩系统从权数量，但必须保证系统/装置独权与方法核心步骤对应。
- 权要 1 在合适时应遵循"数据获取 → 数据处理 → 结果输出"的逻辑。
- 权要 1 中文字数不超过 400 字：简明到能描述完整方案、完整到能展示获得什么结果，但不写分支、调优、异常情况或具体案例（这些放从属权要或说明书）。
- 权要 1 和从属权要的字数、分段粒度参考 `/Users/example/Desktop/Patent/第3-4课的案例资料/案例分享-定稿-一种基于物联网的智能电能表数据采集方法及系统.docx` 的权利要求书：权要编号开头单独成段，后续每个分号结尾的步骤单独成段。
- 每个分号必须保留在段末并另起一行；不得把多个分号步骤挤在同一段。
- 每条权要只用一个句号。
- 使用"所述"进行前序引用（特征第二次及之后出现时，前面加"所述"，第一次引入时不加）。
- 从属权要开头引用独立权要的保护主题时，通常不再重复“一种”；例如写“根据权利要求1所述的配电设备火灾状态评估方法”，不写“根据权利要求1所述的一种配电设备火灾状态评估方法”。独立权利要求首次提出保护主题时可保留“一种”。
- 从属权要开头应完整引用其要展开的权 1 主步骤，不得只引用该步骤的末端结果；例如不能只写“所述获得热源中心坐标，包括”，应完整写出“所述根据所述三维点云模型划分空间体素网格，提取……获得热源中心坐标，包括”。
- 从属权要内部第一次具体得到某一数据、模型、集合、参数或信号时，不加“所述”；后续再次引用该对象时再加“所述”。
- 检查每个被引用对象都存在、命名一致；"所述 XXX"必须在前文有引入基础。
- 每个数据项必须有来源和用途。无明确用途的数据要删掉。
- 每条从属权要只解决一个问题。
- 从属权要应按技术逻辑形成“分支 + 局部链条”的多元化依附关系，不得机械全部依附权要1，也不得机械写成权2→权3→权4→权5的刚性顺序链。可采用类似“权2、权3、权4补充权1；权5补充权3；权6补充权5；权7补充权6；权8补充权3；权9补充权8；权10作为另一保护主题独权或系统/装置权”的结构。该示例不是固定模板，实际应根据技术逻辑调整。
- 常规从属权要的每个子步骤段宜短，避免单段过长；整条从权可包含 2–5 个短步骤段。创新步骤需要展开时，优先拆成多个短步骤段，仍过长时考虑拆成多条从权。
- 使用短步骤；长逻辑拆成多条短步骤。
- 系统/装置权要的模块通常使用"用于"。
- 当方法权和系统/装置权同时存在时，系统/装置独权的模块应与方法权的核心步骤一一对应；如果方法权将某个技术环节拆成独立从权或独立保护点，系统/装置权也应评估是否拆出对应模块。
- 若一个从权内部包含两个相对独立、均有技术贡献的环节，优先考虑拆成两条从权分别保护；例如“生成初步控制信号”和“执行死区补偿得到最终控制信号”可拆分为两个从权，使层次更清楚。

### 特征链条闭合硬规则

- **每个新特征第一次出现时，必须写清来源**：由哪个已有对象经过计算、映射、提取、筛选、转换、训练、匹配、融合或求解得到。不得让“图像灰度矩阵”“强度矩阵”“阈值”“视差深度图”“点云模型”等中间特征突然出现。
- **每个处理动作必须写清四件事**：判断依据、操作对象、处理结果、后续用途。例如“剔除/过滤/筛选”必须说明基于什么依据、从哪个数据对象中剔除、得到什么剩余数据、该剩余数据用于什么后续步骤。
- **每个中间结果必须被后续步骤使用**：得到的数据、矩阵、阈值、集合、序列、模型、参数、信号若没有后续用途，应删除或改写为后续步骤的输入。
- **不要为了显得技术复杂而加入无后续用途的中间特征**：权要优先写真正支撑后续处理的数据基础；每个数据都应进入下一步计算、筛选、聚类、拟合、控制或输出链条。听起来技术性强但后续不用的特征，如未参与定位、判断、建模或控制的法向量、特征值、指标等，应删除或改写为有实际用途的数据。
- **已引入特征后续引用必须加“所述”**：第一次引入特征通常不加“所述”，第二次及以后引用该特征必须加“所述”；避免同一特征前后写法不一致。
- **中间概念不能突然出现**：如“坐标节点”“局部点云数据”“空间目标坐标点”等，第一次出现时必须说明由哪些已有对象构成、从哪里提取或代表什么技术含义。
- **结果命名不能只写“处理后的……”**：应写出处理含义，如“修正后的绕行路径序列”“去噪后的双目视差深度图”“补偿后的控制信号”，避免泛称导致用途和技术效果不清。
- **阈值、参数、系数不能只写“预设/自适应设置/动态确定”**：必须说明确定依据，如根据强度分布、历史数据、统计结果、误差范围、训练目标、工况范围或其他已有对象确定。权要中为保证判断逻辑清楚，可使用“预设阈值/预设终止条件”等表达；说明书中必须补充其确定依据。
- **判断阈值不得由当前待判断结果反向确定**：用于判断的阈值应在判断前已经确定，或由历史数据、标定数据、统计结果、工况范围等独立依据确定；避免“根据当前拟合误差分布确定拟合阈值，再判断当前拟合误差是否小于该阈值”这类循环依赖。
- **跨数据形态转换必须写出转换链条**：图像、灰度矩阵、强度矩阵、深度图、点云、体素、坐标集合、路径序列、轨迹模型、控制信号属于不同技术层级，不能用前一层级的处理动作直接得到后一层级结果。必须写成“输入对象 → 中间处理 → 转换/映射/逆投影/求解 → 输出对象”。
- **不得用过于上位的结果性概念吞掉实际步骤**：如“闭环反馈”“智能控制”“自动调节”“优化处理”“完成操作”“构建模型”“生成策略”“补偿信号”“进行评估”等，必须拆成可限定的技术链条，例如“输入参数 → 控制参数 → 初步控制信号 → 补偿/调整 → 最终控制结果”。
- **创新性步骤必须在权要中展开关键技术链**：如果批注或交底书表明某一步是创新点，不能只写“构建/生成/优化/补偿”；应写成“输入对象 → 关键处理机制 → 中间结果 → 参与最终结果”的链条。例如喷射轨迹模型类步骤应体现“绕行路径序列 → 抛物线修正 → 修正绕行路径 → 喷嘴流量系数 → 曲线拟合 → 喷射轨迹模型”。
- **从属权要按权1主步骤逐条对应展开**：权1先按主技术路线总括，权2开始依次解释权1中的主步骤，如权2解释建模、权3解释热源中心、权4解释物理遮挡区域、权5解释绕行路径、权6解释喷射轨迹、权7解释控制参数/初步信号/死区补偿。不得随意跳步、错位解释或把后一步内容提前塞入前一条从权。
- 权要 1 允许上位概括，链条闭合重点落在从权展开中；当创新点若不写入权要 1 会导致权要 1 无法解决技术问题时，才在权要 1 中压缩写入关键链条，具体算法细节优先下沉到从权和说明书。
- 自检口诀：**来源是否明确、对象是否明确、依据是否明确、结果是否明确、用途是否明确、层级是否跳跃**；任一项不明确，不得写入最终稿。

## 特征命名

- 用功能命名特征，如"数据"、"信息"、"结果"、"指令"、"策略"、"特征"。
- 避免使用"格式"、"文件"、"情况"、"措施"、"方案"、"公式"这类无法清楚指代技术特征的名词。
- 当存在大量具体备选时不要使用宽泛的总称（如"过滤算法"），要写具体操作、模型、规则或处理方法。
- 不要在没有定义范围或判定标准时使用"大"、"小"、"较大"、"较小"、"高"、"低"等含糊命名。
- 不要使用"其"、"此"、"该"等指代不明的代词。
- 不要用"以"连接后续操作步骤；审查员可能把"以"后面的内容当作效果而非操作。
- 区分相似特征命名，例如"第一场景向量"和"第二场景向量"。
- 全文术语必须完全一致，不可缩写或变形。

## 禁用或风险措辞

避免：

- `直接`
- `即时`
- `然后`
- `可以`
- `首先`
- `其次`
- `能够`
- `例如`
- `只有`
- `一定`
- `采用xxx工具`
- `采用xxx模块`
- 没有指明具体技术操作的宽泛措辞（如"过滤算法"）
- 多个近义动词堆叠（如"分析、识别"）——能用一个具体操作时不要堆叠

写真正的操作，而不是说工具/模块去执行。如交底书说"采用数据整合工具对所述...进行填补"，要去掉工具措辞直接写"对所述...进行填补"。

## 公式

- 权利要求中不写公式。
- 权要中如需计算，写为"根据 A 和 B 进行计算，得到 C"。
- 公式放说明书中。
- 用可编辑的字母符号公式，不用中文字符作为公式变量。
- 解释每个参数。
- 检查等号两边的量纲、量级、技术含义。
- 不写本领域技术人员无法实施的不清楚公式。

## 模型与算法

- 训练数据和预测数据通常时间不同，但同类型。
- 训练过程：用历史 A 数据作为输入，历史 B 数据作为输出。
- 使用过程：输入当前 A 数据，得到当前 B 数据。
- 明确模型类型、结构、训练数据、训练方式、损失或目标（相关时）、使用方式。
- 模型训练或参数迭代必须有预设阈值、最大训练次数、收敛条件或其他终止条件。

## 判断步骤

使用以下二者之一：

- `当判定满足xx时，则执行xx操作；当判定不满足xx时，则执行xx操作。`
- `判断是否满足xx，若是，则执行xx操作；若否，则执行xx操作。`

## 说明书

- 摘要字数不超过300字；权要一稿默认不写摘要，全文一稿或用户明确要求时再写摘要。
- 权要定稿后，全文阶段不得修改权利要求书的任何内容；全文阶段仅补写或修订权要阶段未撰写的说明书摘要、摘要附图、发明内容、附图说明、具体实施方式、说明书附图等部分。除非用户明确要求，不得在全文阶段反向改权要、技术领域或背景技术。
- 说明书要清楚、完整、可实施。
- 解释每一条权要步骤。
- 重要步骤、上位概念要详细解释。
- 简单常规内容可简略。
- 说明书与权要对应，但作为最详细的一层：包含实施细节、案例、举例、附图解释。
- 有益效果要给技术原因，不能只下结论。
- 阈值要说明确定方式：常识、实验统计或算法计算。
- 避免"带宽资源：..."这类名词冒号定义句式。
- 全文终稿目标约 1.5–2 万字，除非用户另行说明。

## Markdown 优先撰写

- 对权要一稿和全文一稿，先用 Markdown 撰写，再写入 DOCX。
- 权要一稿时，用 `scripts/disclosure_docx_to_md.py` 把交底书 DOCX 转为案件文件夹下的 `交底书.md`，防止丢失 Word 批注和高亮。
- 权要阶段把 Markdown 草稿保存为案件文件夹下的 `权要稿.md`；全文阶段把 Markdown 草稿保存为案件文件夹下的 `全文稿.md`。
- 先用 Markdown 组织和修订文本层：技术问题、技术方案、技术效果、权要、说明书各节、附图说明、模板功能槽位。
- 写入 DOCX 之前，自检对应 Markdown 草稿：术语一致性、权要引用、数据来源/用途、模板案例性术语、禁用措辞、权要内公式、模型/阈值细节、可实施性、每个模板功能槽位是否满足。
- 通过 Markdown 自检后再写入 DOCX 模板并格式化。
- 直接编辑 DOCX 适合局部修订、批注修订、格式修复、小字符替换，不作为首稿的默认方式。

## 模板文本适配

- 不要把模板字体颜色当作唯一规则。红/蓝字通常是要替换或删除的占位指引，但黑字也可能是固定法律措辞、结构句式或案例性技术内容。
- 模板可能对应一个先前案件，可能含案例性术语。不要把该案件的技术领域、对象名、模块、举例、效果、附图名、保护主体迁移到新案件。
- 保留每个模板槽位的功能，不要逐字复制黑字。把黑色模板措辞适配到当前保护主体和当前稿次。
- 所有技术术语、特征名、模块、数据名、效果、附图说明，全部从当前交底书和当前权要集合构建；模板只提供结构和写作功能。
- 法律/结构句式（背景过渡、"第一方面/第二方面"、实施例引出、系统-方法对应、保护范围结尾、可选保护主体类型）按是否适配当前案件保留、改写或删除。
- 删除或改写只用于另一案中举例的黑色技术内容。
- 仅当符合保护策略和案件类型时，才包含计算机可读存储介质的权要或说明书段落。不要因为模板里有"计算机可读存储介质"就强行套到每个案件。
- 审计模板合规时，检查每个模板槽位的法律/结构功能是否被满足、模板案例性术语是否已清除，而不是检查每句模板原文是否被逐字复制。

## DOCX 格式

- **不要清除模板的页眉**：模板用页眉承载主章节标题（说明书摘要、摘要附图、权利要求书、说明书、说明书附图），分别挂在对应分节（sectPr）的 `headerReference` 上。删除 `word/header*.xml` 等于删除主章节标题，会破坏文件结构。
- **权要一稿 DOCX 只能显示权利要求书、技术领域、背景技术**；说明书摘要、摘要附图、发明内容、附图说明、具体实施方式、说明书附图、图1等标题或页眉不得显示。
- **保留模板资源但按稿次控制可见章节**：权要一稿/二稿可只保留“权利要求书”和“说明书”两个可见页眉及其 `headerReference`，正文只显示权利要求书、技术领域、背景技术；同时应保留模板包内的全部 `word/header*.xml` 资源，避免破坏后续全文一稿恢复摘要、附图和说明书附图。全文一稿再恢复/填充摘要、附图、发明内容、附图说明、具体实施方式等章节。
- 正文段落：宋体、四号、1.5 倍行距，首行缩进 2 个中文字符。
- 模板中以红字（FF0000）出现的内容通常是写作指引或占位符，写入正稿时整段替换或删除。
- 模板中以蓝字（0000FF）出现的内容通常是另一案件的案例性技术示例，全部替换为当前案件的真实内容。
- 完工前在 XML 层级验证：`sectPr` 数量、`word/header*.xml` 数量未减少、`headerReference` 全部保留、各章节正文段落已替换为当前案件文本。

## 附图

- 不要使用交底书中提供的图作为最终申请图，因为这些图可能与已撰写内容不对应。
- 申请图应根据最终权要和说明书重画。
- 用本地 Visio 或 WPS 流程图工具完成最终绘制。
- 不要使用在线流程图截图作为最终申请图。
- 本 skill 可以提供附图设计指引，但最终的图由用户手工绘制并插入。

## 附图设计

对每次全文撰写（`全文1稿/2稿/3稿`），在 `全文稿.md` 末尾追加 `## 附图设计（供手画 Visio 用）` 一节。用户基于这一节在 Visio 中手画实际附图。

### 附图清单规则

默认附图集合：

1. **图 1 — 方法主流程图**（存在方法独立权要时必备）
2. **图 2..N-1 — 子步骤展开流程图**（每个被进一步分解的主权要步骤一张）
3. **图 N — 系统结构图**（存在系统/装置独立权要时必备）

摘要附图默认 = `图 1`。

判断某主步骤是否需要单独成图：

- 该步骤在某条从属权要中被分解为 ≥3 个枚举子步骤，且具体实施方式中使用 `SXX1、SXX2、...` 子编号 → 单独画一张子流程图。
- 仅以平铺段落描述、无子编号 → 不单独画。

### 各类附图的节点措辞规则

**规则 A — 主流程图（图 1）**

- 节点数 = 权要 1 中独立步骤句的数量（通常 3–6 个，按 `；` 分号切分）。
- 每个节点文字 = 权要 1 对应那一句中文，**逐字照抄**（不改写、不压缩）。
- 节点编号 = `S11、S12、...、S1N`，与具体实施方式的编号一致。
- 箭头：单线、单向、自上而下。

**规则 B — 子步骤展开流程图（图 2..N-1）**

- 节点数 = 在被展开的父步骤内部的 `SXX1、SXX2、...` 子步骤数。
- 每个节点文字 = 一段 **≤10 字** 的中文短语，形式为「动作动词 + 产物名」。
  - 从子步骤句末"得到/标记/确认/生成 XXX"中取出产物名 XXX。
  - 前缀加上操作动词（"提取/标记/生成/确认/计算/筛选/..."）。
  - **不要**在这里照抄整句；保持简短。
- 节点编号 = `SXX1、SXX2、...`，继承父步骤编号（父 `S12` → 子 `S121、S122、...`）。
- 箭头：单线、单向、自上而下。

**规则 C — 系统结构图（图 N）**

- 节点数 = 系统独权中模块的个数。
- 每个节点文字 = 系统权要中的模块名，**逐字照抄**（例如 `数据预处理模块`）。
- 箭头按系统权要中模块出现顺序展示数据流，单线、单向。
- 推荐纵向布局，与方法流程图视觉一致。

### 完工前的附图设计验收

报告全文稿完成前，根据"附图设计"节核对：

- 图 1 节点数 == 权要 1 中以"；"分隔的步骤数。
- 图 1 节点文字逐字等于权要 1 各分句。
- 每张子流程图的子节点数等于具体实施方式中 `SXX1..SXXN` 的数量。
- 子流程图节点文字 ≤10 个中文字，且与对应子步骤的产物一致。
- 系统图模块数和模块名与系统独权一致。
- 摘要附图声明与图 1 完全相同。

## 完工自检（报告前）

报告 DOCX 完成前，检查：

- 权要引用的一致性
- 从属权要开头是否完整引用权 1 中被展开的完整主步骤，而非只引用末端结果
- 从属权要引用保护主题时是否去掉多余的“一种”，独立权要首次提出保护主题时是否保留合理
- “所述”是否只用于已有前序基础；从属权要内部首次得到的数据、模型、集合、参数或信号是否未误加“所述”
- 创新性步骤是否被拆成技术链，而非只写“构建/生成/优化/补偿”等结果性概括
- 每个中间结果是否在后续步骤中发挥作用；若批注问“作用是什么”，必须写明该结果如何作为后续输入、依据、约束或控制量
- 判断阈值是否在判断前已有独立确定依据，是否避免由当前待判断结果反向确定阈值的循环依赖
- 方法权与系统/装置权是否对应；方法权拆出的独立保护点是否在系统/装置权中有对应模块或明确不需要同步的理由
- 全文术语一致性
- 数据来源或数据用途不清
- 权要内出现公式
- 说明书内出现不清楚公式
- 阈值缺确定方式
- 缺模型训练/使用细节
- 专利法第 26.3 条 / 实施细则第 20 条的清楚、完整、能够实现问题
- 公式量纲、量级、举例范围、领域可信度
