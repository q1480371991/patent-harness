# 全局规则

本文件是 patent skill 所有阶段默认读取的全局规则。它只承载跨阶段硬性约束和质量约束；阶段专属内容请按 `rules.md` 的阶段读取表继续读取对应文件。

本文件按规则作用范围和强制程度组织：

- **全局规则**：所有稿次、所有块均适用。
- **全局 1级规则**：跨所有块的硬性约束，违反即停笔修正；优先级最高。
- **全局 2级规则**：跨所有块的质量优化约束，优先满足；用于提升规范性、稳定性和交付质量。
- **局部规则**：只作用于特定内容块，如权利要求书、说明书摘要、具体实施方式等。
- **局部 1级规则**：该块的硬性约束，违反会影响专利严谨性、可实施性、保护范围或 DOCX 交付结构。
- **局部 2级规则**：该块的质量优化约束，违反不一定导致稿件不可用，但会降低清楚性、规范性或交付质量。

> 本文件是所有阶段默认强制读取的全局规则文件；旧版规则仅保留在 `docs/archive/` 作为历史备查，正常工作流不得读取或执行。
> 阶段判断与执行流程以 `SKILL.md` 为准；阶段专属强制规则以 `rules.md` 阶段读取表列出的对应文件为准。

## 0. 规则分级总表

| 层级 | 适用范围 | 处理原则 | 示例 |
|---|---|---|---|
| 全局 1级规则 | 所有块、所有阶段 | 必须始终遵守；冲突时优先级最高；违反即停笔修正 | 不照抄交底书、链条闭合、术语一致、DOCX 骨架保留 |

# 全局规则正文

## G1. 文件命名与工作文件规则

### G1-1 全局 1级规则（硬性约束）

- `~/Desktop/Patent/` 下按撰写者分为 `夏晓贝/` 和 `王培元/` 两个一级目录；案件文件夹必须位于对应撰写者目录下。
- 撰写者直接取案件路径中的一级目录名，不再重复询问。案件不在上述两个目录下或路径无法唯一判断时，必须先向用户确认。
- 对外 DOCX 交付文件采用：`案件号-稿次-作者-发明题目全称.docx`（如 `X2607008-全文4稿-夏晓贝-一种弧形LED显示屏亮色度一致性控制方法及系统.docx`），存放在案件文件夹**根目录**。不得使用 `<撰写者>-<稿次>.docx` 简写，不得加 `-留痕` 等状态后缀（留痕/干净属交付状态，写在完工报告里，不进文件名）。
- 案件工作文件统一存放在案件文件夹下的 `docs/` 子目录（无则创建）：`交底书.docx`、`交底书.md`、`权要稿.md`、`全文稿.md`；根目录只放对外交付 DOCX 和老板批注稿。
- 交底书 DOCX 转出的带批注 Markdown 统一命名为：`docs/交底书.md`。
- 权要阶段 Markdown 草稿统一命名为：`docs/权要稿.md`。
- 全文阶段 Markdown 草稿统一命名为：`docs/全文稿.md`。
- `docs/权要稿.md` / `docs/全文稿.md` 恒为“最新基准”，固定文件名不改、不迁移，是所有脚本闸门与各路 auditor 的唯一基准路径；任何稿次都在原文件就地更新，不因稿次推进而改名。
- 每完成一个交付稿次（权要 N 稿 / 全文 N 稿，含一稿与各返修留痕稿），除更新上述固定基准外，必须把该稿定稿时的 md 基准另存一份只读快照到案件 `docs/history/` 子目录（无则创建），命名 `权要N稿.md` / `全文N稿.md`，其 N 与对外交付 DOCX 稿次一致；同一稿次多轮迭代只保留最终交付态（同名覆盖）。稿次追溯以 `docs/history/` 内最新一份快照为准。
- `docs/history/` 快照仅作历史留档，只读不再编辑；脚本闸门、auditor、DOCX 注入一律以固定基准 `docs/权要稿.md` / `docs/全文稿.md` 为输入，不读 history 快照。稿次不写入 `全文稿.md` 的指纹 front-matter——`fingerprint_claims.py --gen` 每次会整块重写该 front-matter，外加的稿次字段会被覆盖。
- 老板批注稿以「审核N-」前缀命名（如 `审核1-案件号-权要1稿-作者-题目全称.docx`），保留原样不覆盖。
- 旧的 `disclosure_annotated.md`、`case_draft.md` 命名不再作为标准；遇到旧案时应规范化改名，避免同一案件中多个草稿名并存。遇到工作文件还散在案件根目录的旧案，应把它们移入 `docs/` 后再继续。
- 本节所称 `docs/` 均指**案件文件夹内**的 `docs/` 子目录；`patent` skill 自身的 `docs/` 目录（如 `docs/archive/`、`docs/install.md`）是技能文档目录，与案件文件无关，不得混用。

### G1-2 全局 2级规则（质量优化）

- 文件名应尽量短而明确，避免同一案件中多个候选草稿名并存。

示例：

- `X2607008-权要1稿-夏晓贝-一种弧形LED显示屏亮色度一致性控制方法及系统.docx`
- `X2607008-全文4稿-夏晓贝-一种弧形LED显示屏亮色度一致性控制方法及系统.docx`

## G2. 交底书阅读与理解规则

### G2-1 全局 1级规则（硬性约束）

- 本节的"深读交底书"义务仅适用于**权要一稿**和**全文一稿**。返修阶段（权要二稿/三稿、全文二稿/三稿、Word 批注返修）默认不重读交底书，按审核人（老板）批注执行；仅当批注要求新增稿件中尚不存在、需回溯交底书原始技术内容时，才按需查 `docs/交底书.md` 对应段落，以守住"不凭空发明"。
- 不要原文照抄交底书。
- 权要一稿、全文一稿撰写前必须先充分理解交底书；未理解清楚时不得起草。
- 必须明确本案要解决的核心技术问题，并锁定一个工业可行的技术问题。
- 必须明确交底书中的技术方案主流程，能复述“输入对象 → 处理步骤 → 输出结果 → 技术效果”的完整链条。
- 必须明确每个关键数据、模型、参数、阈值、设备、模块的来源和用途。
- 创新点以交底书批注为准：本所交底书的 `> 💡 [批注 ...]` 会直接圈定权利要求书的创新点（落在哪几个步骤/技术特征上）。撰写时**按批注圈定的创新点展开**，不自行另判创新点；批注未圈定的步骤按支撑/常规环节处理，不擅自升格为创新特征。仅当批注缺失、或批注圈定的创新点在交底书技术方案中找不到支撑时，才回问用户，不凭空判定。
- 必须明确预期技术效果及其技术原因。
- 必须围绕“技术问题—技术方案—技术效果”展开。
- 必须阅读 `交底书.md` 中的 `> 💡 [批注 ...]` 行；批注圈定的创新点是撰写创新特征的**唯一依据**，并作为老板关注点、撰写风险点处理。
- 若批注与正文技术链条冲突，或交底书逻辑不通、技术上不自洽，停下来询问用户，不要凭空发明。
- 必须判断关键步骤是否具有输入、处理、输出；模型/算法是否具有训练数据、使用数据、输出结果；阈值、参数、判断条件是否具有确定依据。
- 必须判断是否存在突然出现的中间概念，以及图像、点云、路径、控制信号等跨数据形态转换是否闭合。

以下任一情况出现，不得直接起稿：

- 找不到核心技术问题。
- 权要 1 的主流程无法从交底书中支撑。
- 关键特征来源不明。
- 数据只出现但没有用途。
- 交底书只有效果口号，没有技术方案。
- 批注与正文逻辑冲突。
- 无法判断保护主题是方法、系统/装置还是两者都有。

### G2-2 全局 2级规则（质量优化）

- 起草前优先形成内部结构提纲，不需要默认输出，除非用户要求。
- 内部结构提纲宜包括：技术领域、背景问题、核心方案、关键步骤、可选步骤、系统/装置模块、预期效果、附图素材、风险点。
- 起草前宜判断哪些内容适合进权要 1，哪些适合进从权，哪些只适合进说明书。
- 起草前宜判断是否存在方法权、系统/装置权、存储介质权的保护空间。
- 起草前宜判断交底书给出的附图是否与最终权要链条一致。
- 阅读后优先把技术问题、核心方案、预期效果用简短内部提纲理顺，再进入各块撰写。

## G3. 技术链条闭合规则

### G3-1 全局 1级规则（硬性约束）

撰写任何技术特征时，必须满足来源、对象、依据、结果、用途五要素闭合。

- **每个新特征第一次出现时，必须写清来源**：由哪个已有对象经过计算、映射、提取、筛选、转换、训练、匹配、融合或求解得到。不得让“图像灰度矩阵”“强度矩阵”“阈值”“视差深度图”“点云模型”等中间特征突然出现。
- **每个处理动作必须写清四件事**：判断依据、操作对象、处理结果、后续用途。例如“剔除/过滤/筛选”必须说明基于什么依据、从哪个数据对象中剔除、得到什么剩余数据、该剩余数据用于什么后续步骤。
- **每个中间结果必须被后续步骤使用**：得到的数据、矩阵、阈值、集合、序列、模型、参数、信号若没有后续用途，应删除或改写为后续步骤的输入。
- **中间概念不能突然出现**：如“坐标节点”“局部点云数据”“空间目标坐标点”等，第一次出现时必须说明由哪些已有对象构成、从哪里提取或代表什么技术含义。
- **叙述性新术语首现即时定义（含补写/返修新造词）**：本条同样适用于解释段自造的叙述性名词（如“展平基准面”“邻域搜索半径”“标准网格节点集合”“前景像素”“像素标签”一类）——补写或返修中新造任何名词，须在首现句内或紧邻句给出定义（指什么、由哪一步产生/如何取值），否则删词改用既有名称；返修轮的新词闸门执行判据见 `revision.md` G9-1。
- **跨数据形态转换必须写出转换链条**：图像、灰度矩阵、强度矩阵、深度图、点云、体素、坐标集合、路径序列、轨迹模型、控制信号属于不同技术层级，不能用前一层级的处理动作直接得到后一层级结果。必须写成“输入对象 → 中间处理 → 转换/映射/逆投影/求解 → 输出对象”。
- **不得用过于上位的结果性概念吞掉实际步骤**：如“闭环反馈”“智能控制”“自动调节”“优化处理”“完成操作”“构建模型”“生成策略”“补偿信号”“进行评估”等，必须拆成可限定的技术链条；控制类链条应写清“输入参数 → 控制参数 → 初步控制信号 → 补偿或调整 → 最终控制结果”。
- **创新性步骤必须展开关键技术链**：至少写明“输入对象 → 关键处理机制 → 中间结果 → 参与最终结果”。任何分块展开不得跳步、错位，或把后一步内容提前塞入前一步；从属权要、发明内容和具体实施方式均应按该链条逐层展开。

### G3-2 全局 2级规则（质量优化）

- 不要为了显得技术复杂而加入无后续用途的中间特征；每个数据都应进入下一步计算、筛选、聚类、拟合、控制或输出链条。
- 同一数据链路上不要堆叠多次仅以平滑/去噪为目的的滤波操作；若某滤波步骤只是单纯平滑数据滤除噪音（而非筛选特定数据），且链路后续另有去噪环节，应删除该滤波步骤，避免数据过度平滑。
- 听起来技术性强但后续不用的特征，如未参与定位、判断、建模或控制的法向量、特征值、指标等，应删除或改写为有实际用途的数据。
- 结果命名不宜只写“处理后的……”，应写出处理含义，如“修正后的绕行路径序列”“去噪后的双目视差深度图”“补偿后的控制信号”。

**自检口诀**：来源是否明确、对象是否明确、依据是否明确、结果是否明确、用途是否明确、层级是否跳跃。任一项不明确，不得写入最终稿。

## G4. 特征命名与前序引用规则

### G4-1 全局 1级规则（硬性约束）

- 全文术语必须完全一致，不可缩写或变形。
- “所述”前序引用规则：特征第一次引入时不加“所述”；第二次及之后引用该特征必须加“所述”。检查每个被引用对象都存在、命名一致；“所述 XXX”必须在前文有引入基础。
- **物理设备与采集硬件不加“所述”（设备指代例外，本条为唯一出处；权要与说明书同源）**：作为方法执行平台或数据采集来源的物理实体——无人机及其机体/机身、各类相机与视觉传感器（如前向、后向视觉传感器）、惯性测量单元、光敏元件、机载传感器等——一律**不加“所述”**，第二次及以后再次出现仍直接用名称（写“前向视觉传感器”“无人机机体”，不写“所述前向视觉传感器”“所述无人机机体”）。上一条“所述”回指只作用于方法链条产生或加工的**数据流对象**（图像序列、评分、通道、约束、参数、模型、阈值、指令、位姿等）。**边界**：系统/装置独权的结构部件（存储器、处理器、计算机程序）按 `claims.md` L1-1 计算机设备式套话仍写“所述存储器/所述处理器”，不属本例外。判据：被指代对象是“方案的物理载体或采集/运算硬件”→不加“所述”；是“方法链上产生或加工的数据对象”→按上条首次不加、后续加“所述”。
- 不要使用“其”“此”“该”等指代不明的代词。
- 不要用“以”连接后续操作步骤；审查员可能把“以”后面的内容当作效果而非操作。

### G4-2 全局 2级规则（质量优化）

- 用功能命名特征，如“数据”“信息”“结果”“指令”“策略”“特征”。
- 特征命名不要太长，核心名词一般 4–6 个中文字，只保留最核心的特征词；命名不需要与交底书保持一致，交底书中冗长的描述性名称应压缩（如“初始连续位移坐标序列”压缩为“初始位移序列”）。
- “第一/第二”等序号限定词仅在确需区分两个同类特征时使用；全文只有一个该类特征时，序号属于无用限定信息，应删除。
- 命名过长时可把限定信息与特征名词用“的”隔开，首次引入写“限定语的核心名词”（如“加速度的波动特征值”），后续引用只引用核心名词（“所述波动特征值”），避免长名称反复整体出现。
- 避免使用“格式”“文件”“情况”“措施”“方案”“公式”这类无法清楚指代技术特征的名词。
- 结果性命名避免“xx处理结果”式的动作复述（如“差值平滑处理结果”），应命名为有技术含义的数据对象（如“平滑差值序列”）。
- 当存在大量具体备选时不要使用宽泛总称（如“过滤算法”），要写具体操作、模型、规则或处理方法。
- 不要在没有定义范围或判定标准时使用“大”“小”“较大”“较小”“高”“低”等含糊命名。
- 区分相似特征命名，例如“第一场景向量”和“第二场景向量”。

## G5. 禁用或风险措辞规则

### G5-1 全局 1级规则（硬性约束）

避免：

- `直接`
- `即时`
- `然后`
- `可以`
- `首先`
- `其次`
- `能够`
- `例如`
- `只有`
- `一定`
- `采用xxx工具`
- `采用xxx模块`
- 没有指明具体技术操作的宽泛措辞（如“过滤算法”）
- 名词冒号定义句式（如“带宽资源：...”）
- **AI 元叙述 / 自辩话术（1级）**：向读者或审查员解释“本实施例为何这样写 / 为何不写某内容”的句子一律删除。典型形态——“不在本实施例中编造固定数值”“具体数值随……变化”（其后不给任何示例值）“本实施例保留该上位名称以与权利要求书保持一致”“不再另行重复引入无必要的算法名称”“为与权利要求书保持一致，故……”。**判据**：句子主语是“本实施例/本文/本方案”且宾语为写作动作（编造/保留/引入/重复/省略/展示）而非技术动作，即属元叙述。处理：删除该句；若它替代了本应给出的技术内容（示例值、展开、定义），按 G6-1 补回真实内容，不得以自辩句搪塞。

### G5-2 全局 2级规则（质量优化）

- 避免多个近义动词堆叠（如“分析、识别”）；能用一个具体操作时不要堆叠。
- 写真正的操作，而不是说工具/模块去执行。如交底书说“采用数据整合工具对所述...进行填补”，要去掉工具措辞直接写“对所述...进行填补”。

## G6. 公式、模型、阈值与判断规则

### G6-1 全局 1级规则（硬性约束）

- 权利要求中不写公式。
- 权要中如需计算，写为“根据 A 和 B 进行计算，得到 C”。
- 公式放说明书中。
- 说明书中的所有公式一律写成 **LaTeX 源码**并独立成段：`全文稿.md` 中写纯 LaTeX 源码文本，**不带 `$`/`$$` 定界符**；公式段后必须紧跟参数解释段。**公式不加编号（无 (1)(2)(3) 等式号）**——专利撰写惯例，公式独立成段、不挂章节式号；`omml_formulas.py gen` 不得传 `--number`，`check` 的 `formula_numbering_count` 须为 0。
- 公式写入 DOCX 时默认转为**原生可编辑二维公式**（WPS/Word 均可编辑）：用 `scripts/omml_formulas.py gen` 把每条 LaTeX 经 pandoc 转成块级 `m:oMathPara` 公式段整段注入，收尾对交付 DOCX 依次执行 `omml_formulas.py fix-settings`（数学字体与 mathPr 修正）和 `omml_formulas.py check`（公式健康体检）；不得把 LaTeX 源码文本原样留在交付稿正文，不得要求用户手动进 Word 编译公式。仅当 pandoc 不可用时才回退为纯 LaTeX 文本写入（Times New Roman），并在完工报告注明回退原因。执行细节与陷阱的唯一出处：`references/rules/docx-template.md` G8-3、`references/cases/docx-execution.md` C-DOCX-8。
- 用可编辑的字母符号公式，不用中文字符作为公式变量。
- **行内引用的符号也须做成原生公式，禁用 Unicode 上下标充数**：参数解释段与正文里引用公式符号时，写成行内 LaTeX 并以 `$…$` 定界（与本节“块公式独立成段、不带 `$` 定界符”相区分——**块公式无 `$`、行内公式用 `$…$`**），注入时转为原生行内 `<m:oMath>`。**不得用 Unicode 上/下标字符（如 s₁、₀、⁻¹）冒充**：WPS 会把 Unicode 下标渲染成全角 `s2`、且上标下标不叠放，等同未编译，与上一条“不得把 LaTeX 源码原样留在交付稿正文”同属公开不充分。含大写字母下标（如 `\Sigma_I`、`r_I`，无对应 Unicode 下标）时改用数字下标（`\Sigma_1`、`r_1`）或马氏型 `r^{T}\Sigma^{-1}r` 规避。行内注入执行细节见 `references/rules/docx-template.md` G8-3。
- 解释每个参数。
- **公式展开最小必填清单（1级，完整性级；公式类展开“算够”的唯一判据）**：说明书每个公式必须逐项给全五项——①每个符号；②每个符号的含义；③单位（无量纲则注明无量纲）；④取值范围；⑤本实施例示例值。缺任一项即公式公开不充分 FAIL。例：径向基核函数须给 K、x、y、‖x−y‖、γ 每个符号的含义与 γ 的作用/取值。
- 检查等号两边的量纲、量级、技术含义。
- 不写本领域技术人员无法实施的不清楚公式。
- 明确模型类型、结构、训练数据、训练方式、损失或目标（相关时）、使用方式。
- **深度学习/机器学习模型展开四维度测度（1级；模型类为长尾类，用测度而非固定清单）**：涉及可训练模型（CNN/全连接、SVM、隐马尔可夫、孤立森林、核方法等）时，展开须同时过四个测度——（a）可复现：本领域技术人员据此能复现该模型的构建与运算（含取值）；（b）全覆盖：模型每个参与运算的环节（层/核/激活/核函数/贡献率阈值等）均有交代；（c）落地：每个数值/阈值/超参有确定依据与本实施例值；（d）闭环：训练输入来源 ✓ 运算 ✓ 输出送下游 ✓ 三段不悬空。四测度均过方为充分；任一维缺失按公开不充分处理。新被审核点名、原不在测度可直接命中的模型展开维度，按 `revision.md` 学习闭环升格为本节固定必填项。
- 当方案包含训练/预测模型时，必须明确训练阶段的历史输入、历史输出或标签，以及使用阶段的当前输入、当前输出；训练数据和预测数据通常应同类型但时间不同，若不满足需说明原因。
- 模型训练或参数迭代必须有预设阈值、最大训练次数、收敛条件或其他终止条件。
- 阈值、参数、系数不能只写“预设/自适应设置/动态确定”，必须说明确定依据。权要中为保证判断逻辑清楚，可使用“预设阈值/预设终止条件”等表达；说明书中必须补充其确定依据。
- 说明书中补充阈值/参数确定依据时，不能只罗列“来自哪些数据”，必须写出对这些数据所做的具体动作（统计、换算、取分位值、求上界/下界、标定等），使本领域技术人员可复现其取值。
- 权利要求中尽量不要单独写“判断是否满足xx”的判断步骤；单独写判断步骤就必须把“若是/若否”两个分支都写出来，徒增负担。条件触发类逻辑优先写成“若xx，则执行xx操作”的单分支形式，把判断条件与后续动作合并为一步；仅当两个分支均有实质技术动作时，才使用以下二者之一：
  - `当判定满足xx时，则执行xx操作；当判定不满足xx时，则执行xx操作。`
  - `判断是否满足xx，若是，则执行xx操作；若否，则执行xx操作。`
- 判断阈值不得由当前待判断结果反向确定；用于判断的阈值应在判断前已经确定，或由历史数据、标定数据、统计结果、工况范围等独立依据确定，避免”根据当前拟合误差分布确定拟合阈值，再判断当前拟合误差是否小于该阈值”这类循环依赖。
- **判断分支展开最小必填清单（1级；判断类“算够”的唯一判据）**：说明书判断步骤须逐项过三项——①分支数与权要一致（说明书不得比权要多分支或少分支）；②权要为双分支（若是/若否均有实质动作）时两个分支都写，权要为单分支（若…则…）时说明书也只写触发分支、不得补出另一分支；③句式用本节上述两种规定句式之一。三项任一不符即 FAIL。
- 说明书中出现”确定/计算某个结果”但未给出具体计算方式时，必须补充可实施的计算公式或算法步骤，避免公开不充分；空间聚类后的收敛点/质心应补充加权质心公式；涉及时间变化率/导数时应补充差分公式并说明采样间隔。
- 统计学操作术语（上分位值、下分位值、分位数、归一化、标准化、中心化等）在说明书中出现时，必须紧跟算术动作展开：对哪个数据集合、做什么排序/求和/相除、取第几百分位或除以什么、得到什么，并给出本实施例示例值；不得以术语本身作为“确定依据”的终点。
- **统计术语展开最小必填清单（1级；统计术语“算够”的唯一判据）**：每个统计学操作术语须逐项给全五项——①作用的数据集合；②所做操作（排序/求和/相除/中心化等）；③取第几百分位或除以什么（分位/归一化的具体锚点）；④得到什么结果；⑤本实施例示例值。缺任一项 FAIL（如“下分位值”须写清：对该维历史样本升序排序、取第 5 百分位、得下界、示例值 =X）。
- 说明书中的数量词禁用“若干个”“多个”（权要中允许“多个”）；必须写具体符号（如前 k 个）并在本块内给出示例取值与选取理由。**适用边界**：说明书中对权要分句原文的复述（L6 发明内容对应句、L8 集中罗列段/展开段入口句/从权分句列项）以 L8-0 同构逐字为准，复述行中来自权要原文的“多个”不视为违规（`check_hard_rules.py --claims-md` 自动豁免）；本条只约束说明书自写的解释性表述。
- **量数词阿拉伯数字化（1级）**：说明书中表具体数量、比例、区间的中文数字一律改阿拉伯数字——“三至五”→“3 至 5”，“百分之九十”→“90%”，“零至一”→“0 至 1”，“之和为一”→“之和为 1”。作为语言习惯的序数/成语（如“第一”“三维”“二者”“两个分支”）不在此列。权要与说明书均适用此书写规范。

### G6-2 全局 2级规则（质量优化）

- 阈值确定依据可来自强度分布、历史数据、统计结果、误差范围、训练目标、工况范围或其他已有对象；权要中出现“预设阈值/预设终止条件”时，说明书中必须补充对应确定依据。
- 在说明书中，阈值的确定方式可来源于：常识、实验统计、算法计算。

## G7. Markdown 优先撰写规则

### G7-1 全局 1级规则（硬性约束）

- 对权要一稿和全文一稿，先用 Markdown 撰写，再写入 DOCX。
- 权要一稿时，用 `scripts/disclosure_docx_to_md.py` 把交底书 DOCX 转为案件文件夹下的 `docs/交底书.md`，防止丢失 Word 批注。
- 全文一稿的 `docs/全文稿.md` 必须按 `references/rules/full-draft.md` 的"全文稿分块撰写法"逐块写、逐块自检，不得一次性生成全文长文。
- 写入 DOCX 之前，按当前阶段包含的块逐块执行自检清单。
- 通过 Markdown 自检后再写入 DOCX 模板并格式化。

### G7-2 全局 2级规则（质量优化）

- 权要阶段把 Markdown 草稿保存为 `docs/权要稿.md`；全文阶段把 Markdown 草稿保存为 `docs/全文稿.md`。
- 先用 Markdown 组织和修订文本层：技术问题、技术方案、技术效果、权要、说明书各节、附图说明、模板功能槽位。
- 直接编辑 DOCX 适合局部修订、批注修订、格式修复、小字符替换，不作为首稿的默认方式。
- 修改专利 DOCX 时，若用户已明确指定原文件路径并要求直接修改，不再默认创建 `.bak` 等备份文件；仅在不可逆的大范围覆盖、批注原稿保护或用户要求备份时先确认。
