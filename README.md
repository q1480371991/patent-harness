# Patent Harness

面向**长流程专业写作**的领域 Harness。当前以 Claude Code Skill 的形式加载，也跑在 Pi 等其它 Host Harness 上。

> **为什么是 Harness 而不是 Skill**
>
> 本项目不自带 LLM 运行时。它跑在 Claude Code / Pi 这类 **Host Harness**（提供模型循环、工具调用、文件系统、子 agent）之上，自己实现的是**领域编排层**——规则路由、确定性闸门、多路审计编排、经验回流。
>
> ```
> ┌───────────────────────────────────────────────────┐
> │  Host Harness：Claude Code / Pi / …               │
> │  提供：LLM 循环、工具调用、文件系统、子 agent        │
> ├───────────────────────────────────────────────────┤
> │  Patent Harness（本项目）                          │
> │  阶段化工作流 · 规则按需路由 · 确定性闸门           │
> │  多路审计编排 · 三级降级链 · 经验回流              │
> └───────────────────────────────────────────────────┘
> ```
>
> 编排层与领域规则库是分离的：换一个专业领域，置换的是规则库与模板资产，编排骨架不变。

---

## 它解决什么问题

高约束专业文档（权利要求书、说明书、检索报告……）的生成，难点不在"写不出来"，而在三件事：

1. **约束量远超上下文预算**。一个成体系的撰写规范可以到十几万字，不可能每次全量喂给模型；但漏读一条就可能返工。
2. **机械错误会污染下游**。编号、术语、引用基础、公式参数量纲——错一处，下游整段跟着错，且模型自己审不出来。
3. **质量判断无法全交给模型**。规则能判的（格式、结构、数值自洽）和规则判不了的（方案合理性、行业惯例）必须走不同通道，用不同判据。

本项目把这条链路组织成一条**带多重质检的工作流**：知识加载 → 工具调用 → 多路并行审查 → 留痕返修 → 经验沉淀。

## 六个机制

### 任务规划与流程编排（Plan-and-Execute）

用 sha1 指纹锁实现**上游产物冻结**：分阶段模式下，上游定稿后被钉进下游文档头部，下游撰写期间一旦变动就硬停、要求重新同步，避免"上游一改、下游整段返工"。另有直写模式，不冻结，一轮写完整篇。

### 工具调用与确定性校验

用 **27 个确定性校验脚本（10,520 行）** 实现机械与语义的分工：能判定的存成结构数据，判不了的标成可疑项交 subagent 定性。交付前跑固定清单里的 **11 项闸门**，任一不过就阻断回修——机械错误不靠模型兜底。

脚本按职责分层：规则硬约束 / 跨块结构 / 上游与下游对齐 / 公式健康 / 文档骨架 / 版本时序。

### 上下文工程与知识路由

用**三档渐进式披露**实现规则按需加载：

| 档 | 含义 |
|---|---|
| 必读核心 | 该阶段每次都加载 |
| 触发式按需 | 命中触发条件才加载 |
| 禁止默认读取 | 明确列出不该读的 |

规则不整篇读入，按标题切出所需那节；**切的位置另有校验脚本核对**，防止切空后静默返回空结果。

### 多 Agent 协作（Multi-Agent）

用 **4+1 路并行审查**实现多视角交叉验证：

- **4 路一致性审查**（权要 / 内容 / 实施方式 / 全局），脚本全过后并行启动，各读各的规则包，有 1 级否决权；
- **1 路外部视角复核**，**契约明文禁止读取本项目规则库**，无否决权、只出疑点清单。

第 5 路的存在理由是**判据来源不同**：前 4 路用本项目的标准做一致性检查，第 5 路用领域常识做正确性检查。一个内部完全自洽的方案可以整体不合常理——实测中，数值量级错误、算式错误这类硬伤只被第 5 路抓到过。

各路互不共享假设、也不互看报告，结论由主 agent 汇总成回修清单逐条裁决。

### 任务降级与兜底

三级降级链（并行编排 → 逐路派发 → 主 agent 串行），累计 3 次失败自动切换并锁死，避免工具不可用时任务整体卡死。降级按路隔离——失败那一路不影响其余；每次降级写进完工报告首行，**工具环境再差也不中断主流程，但降级不静默**。

### 经验沉淀与规则治理

每次交付后产出一份复盘，把审核意见按**准入闸**逐条判定是否升格进规则库：

- 进规则需同时满足：跨案通则 / 判据可复核 / 有真实规避价值
- 不满足的只归档，**不为凑完整度强行升格**

同时治理规则库自身的膨胀：同节具名条设上限、必读文件设软上限、各阶段读取量留基线（超基线 10% 触发一次「这条规则该不该进必读层」的审查）。

## 快速开始

```bash
# 1. 环境自检（检查 Python 依赖、外部工具、插件）
python scripts/check_env.py --json

# 2. 补齐 pip 侧依赖
python scripts/check_env.py --fix

# 3. 跑测试
python -m pytest tests/ -q
```

**依赖**：Python 3.10+。可选 `pandoc`（用于把公式转为原生 OMML；缺失时公式回退为纯文本，不阻断工作）。

**回归装置**（可选）：需指向本地案卷目录，未设置则自动跳过。

```bash
export PATENT_CASES_DIR=/path/to/cases   # Windows: set PATENT_CASES_DIR=...
```

## 落地

已在 4 人撰写团队日常使用，累计产出 40 篇以上专业申请文件，持续迭代中。

每次交付后做一次复盘：审核意见 → 准入判定 → 固化成规则或机械闸门。**能机械判定的直接固化成闸门，判不了的才留作文本规则**——规则库随案件增长而不膨胀。

## 设计取舍

**为什么机械判定优先于模型判定**
能写成脚本的绝不交给模型。模型的判断有抖动、成本高、且无法在 CI 里复现；脚本判定毫秒级、免费、100% 稳定。模型只用来处理"代码搞不定但能结构化描述"的部分。

**为什么外部视角那一路禁止读自家规则库**
一旦它读了本项目的规则，就变成了"用我们的标准审我们的稿"，与其存在理由（提供不共享假设的第二意见）相悖。实测确认两者不可互相替代。

**为什么模板句要建唯一副本**
格式与套话类问题不交给模型自由发挥：模板句集中在一处渲染、整句粘贴只填槽位，再做双层逐字校验。能固定下来的就用脚本或填空模板固定，不以文本规则的形式交给 LLM。

**为什么规则库要治理膨胀**
规则越多，每次加载的上下文越贵、判断质量反而下降。所以设了三道限：同节条数上限、单文件行数软上限、阶段读取量预算。
